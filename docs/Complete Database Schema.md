## 1. Scope and interpretation

The Laravel migration directory contains 39 migration files which produce **38 named tables** in an isolated migration run. The data dictionary below is based on those migrations, their final schema after all migrations, and the declared application schema. It does not describe the contents of `database/database.sqlite`; no user/business rows were read.

Laravel schema types are reported in application terms. `id()` / `foreignId()` are PostgreSQL big-integer identity/reference declarations; `string()` is `varchar(255)` unless a length is specified; `text()` and long text are text; `decimal(10, 2)` is numeric precision/scale; `json()` and `jsonb()` retain those JSON types on PostgreSQL. `unsignedInteger()` is an application declaration; PostgreSQL itself has no unsigned integer type. Defaults and nullability below are migration-declared. Where a migration does not declare a constraint, the document does not infer one from UI validation.

`created_at` and `updated_at` are nullable unless stated otherwise when generated by Laravel's `timestamps()`. Primary key generation is identified per table. String lengths shown as 255 are Laravel's default when the migration calls `string()` without a length.

The 38-table list includes Laravel framework/runtime support tables. The direct Supabase SQL and the independent FastAPI service SQL add functions/policies/triggers and service support tables beyond Laravel migrations; those are listed separately in §4. Supabase-managed `auth.*` and extension internals are external platform objects and could not be enumerated from this repository.

## 3. Laravel migration data dictionary

- `name`: varchar(255), NOT NULL.

- `icon`: varchar(255), NULL.
- `is_active`: boolean, NOT NULL, DEFAULT `true`.
- `created_at`, `updated_at`, `deleted_at`: timestamp, NULL.

Purpose: inventory item catalogue and stock state.

- `id`: generated bigint primary key.
- `item_code`: varchar(255), NOT NULL, UNIQUE.
- `name`: varchar(255), NOT NULL.
- `description`: text, NULL.
- `category_id`: foreign bigint, NOT NULL; FK to `inventory_categories.id`, delete cascades.
- `quantity`: integer, NOT NULL, DEFAULT `0`.
- `unit`: varchar(255), NOT NULL, DEFAULT `pcs`.
- `unit_cost`: decimal(10,2), NULL.
- `status`: varchar(255), NOT NULL, DEFAULT `available`.
- `condition`: varchar(255), NOT NULL, DEFAULT `good`.
- `location`, `image_path`: varchar(255), NULL.
- `low_stock_threshold`: integer, NOT NULL, DEFAULT `5`.

- `created_at`, `updated_at`, `deleted_at`: timestamp, NULL.
- `lock_version`: integer, NOT NULL, DEFAULT `1`.

- `qr_token`: varchar(255), NULL, UNIQUE.
- Indexes declared: `(category_id, status)`; `item_code` (also unique).

## 4. Supplemental SQL objects and schema caveats

### 4.1 `database/supabase/mobile_backend.sql`

The supplemental SQL:

- Creates/restricts `mobile_return_idempotency`, `mobile_borrow_idempotency`, and `mobile_recent_request_dismissals` if absent.
- Defines 16 PostgreSQL functions: `link_mobile_employee`, `sync_employee_password_to_auth`, `mobile_employee_id`, `mobile_assert_access`, `mobile_employee_profile`, `mobile_inventory_lookup`, `mobile_inventory_search`, `mobile_request_payload`, `mobile_list_borrow_requests`, `mobile_dashboard`, `mobile_dismiss_recent_request`, `mobile_create_borrow_request`, `mobile_cancel_borrow_request`, `mobile_returnable_items`, `mobile_return_borrow_items`, and `mobile_update_employee_name`.
- Installs triggers to link confirmed Auth users to active employees and synchronize password changes.
- Enables RLS on the listed tables, revokes broad client table access, grants authenticated function execution, adds an employee-scoped Realtime select policy on `borrow_requests`, and conditionally adds that table to the Supabase Realtime publication.
- Uses `SECURITY DEFINER` functions with a fixed `search_path = public`.

These objects are established by repository SQL, not confirmed to exist in a live Supabase project. Supabase's `auth.users`, `auth.mfa_factors`, `auth.uid()`, JWT claims, `anon`/`authenticated` roles, and the Realtime publication are managed/external platform objects.

### 4.2 `mobile-service/sql/001_mobile_service.sql` and `002_mobile_service_grants.template.sql`

The independent FastAPI service setup creates `mobile_login_attempts` and `mobile_api_rate_limits` and uses the `mobile_borrow_idempotency` table. It configures RLS/revokes for service-owned idempotency data and documents a dedicated `rgv_mobile_api` principal with scoped grants. `002_mobile_service_grants.template.sql` creates the service principal and grants columns/table access; the principal password is entered out of band and is intentionally not reproduced here.

- `mobile_login_attempts`: `key` char(64) primary key; `attempts` smallint NOT NULL DEFAULT `0` with `CHECK (attempts >= 0)`; `window_started_at` timestamptz NOT NULL; `updated_at` timestamptz NOT NULL DEFAULT current timestamp; index on `window_started_at`.
- `mobile_api_rate_limits`: `key` char(64) primary key; `hits` integer NOT NULL DEFAULT `0` with `CHECK (hits >= 0)`; `window_started_at` timestamptz NOT NULL; `updated_at` timestamptz NOT NULL DEFAULT current timestamp.
- `mobile_borrow_idempotency` is defined compatibly by its Laravel migration and is reused by the FastAPI service: `(employee_id, idempotency_key)` primary key, request hash, JSONB response, timestamp, and employee FK/cascade as detailed in §3.5.

The service also reads/writes existing Laravel tables such as `users`, `roles`, `model_has_roles`, `inventories`, `borrow_requests`, `borrow_items`, `personal_access_tokens`, `notifications`, `notification_preferences`, `login_history`, `audit_logs`, and `activity_log`. Those shared tables are described above. No service grant was applied or verified against a live database in this task.

### 4.3 Differences and limits

- Migration schema was expanded only in an isolated in-memory SQLite environment to inspect final columns/relationships. This verifies Laravel migration execution and application-level declarations, not the live PostgreSQL catalog.
- PostgreSQL-specific RLS, functions, grants, extensions, triggers, and Supabase managed objects cannot be fully verified by SQLite migration execution.
- Direct Supabase SQL and FastAPI service SQL are separate setup paths. Their similar table names do not prove that both paths are applied or used in production.
- The database configuration and documentation describe Supabase PostgreSQL as the canonical production store; this task did not connect to it.
- Character bounds beyond the listed explicit migration lengths rely on Laravel `string()` defaults. Application validation limits are not database constraints.

Polymorphic associations (`model_has_roles.model_id`, tokenable fields, audit/activity subjects) do not have a conventional FK to each possible model table. The mappings table stores source/target keys as generic text and does not declare business-row foreign keys.

## 6. Important data operations and integrity

- `BorrowService` uses database transactions and row locks to verify inventory availability, reserve stock, transition requests, and restore stock on rejection/cancellation/return.
- FastAPI request handlers use parameterized SQL and PostgreSQL transactions/row locks for the same class of workflow.
- Mobile borrow/return SQL functions and service tables persist idempotency keys and response data to prevent duplicate stock movement on retry.
- The migrations define primary/foreign keys, unique identifiers, indexes, defaults, soft-delete timestamps, and version counters. Status/date/quantity validation in controllers/services is application-level unless a schema constraint is listed.
- Eloquent relations describe associations in code; only the FK constraints above are database-enforced by the migrations.
- The database backup/restore and SQLite-to-Supabase merge process are documented in `docs/deployment.md` and `docs/data-migration.md`. Neither live backup/restore nor a data migration was performed for this document.
