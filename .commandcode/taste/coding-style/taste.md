# Coding Style Preferences

- Prefers never hardcoding database passwords or other secrets in source code or prompts; uses environment variables (e.g., `DATABASE_URL`, `DB_PASSWORD`) instead. Confidence: 0.95
- Prefers not fabricating or guessing missing data values; uses `NULL`/defaults/empty fields and flags ambiguous records for review rather than assuming. Confidence: 0.9
- Prefers the database as the single source of truth over hardcoded arrays or demo JSON. Confidence: 0.85
- Wants MySQL (not PostgreSQL/Supabase) as the project's relational database; expects the schema, config, containers, CI and backup/restore paths moved over accordingly rather than left dual-engine. "Remove all supabase related" means a total purge, not a driver swap with leftovers: delete the service/exception classes, custom Postgres connection classes, PL/pgSQL-only migrations, the Supabase auth column and its migration, `pgsql` connection config, all `SUPABASE_*` env vars, dead Postgres-only code branches (psql restore paths, `pg_dump` messages, `TO_CHAR`/advisory-lock branches) and provider-specific docs — while keeping the real tables those migrations created. Confidence: 0.8
- The Flutter app must be wired to the team's Laravel backend, not to an external BaaS: the app talks only to Laravel's REST API (`/api/v1/mobile/*`) with its own auth token, and Laravel is the single source of identity — an admin creates the employee in Laravel, and that employee logs into the app with the same credentials and can use every app feature. Remove Supabase/other third-party SDK coupling from the mobile source rather than keeping both paths, and make any external identity sync optional so employee creation never depends on it. (This supersedes the earlier "Flutter independent, shared Supabase only" contract.) Confidence: 0.8
- Authentication must be server-verified, not device-cached: corrected an "offline-first" login design by demanding the app be "strictly… online" because every login has to reach the backend (Supabase) and validate an account created by the admin. Don't add offline credential caches, stored password hashes/verifiers, or local session restore — only the token plus a server-confirmed profile may persist, and a session/token that can't be checked online is treated as invalid. Confidence: 0.8
- Wants the native (Flutter) app's theme kept visually consistent with the website's palette — when asked to "match the theme/colors," extract exact hex values and status→color mappings from the website's design system (tailwind.config.js, resources/css/app.css, Blade badge classes like `badge-mantis-*`) and apply them precisely to the Flutter theme constants and widgets, rather than approximating with similar tones. Confidence: 0.7
- In the Laravel Blade app, scope feature widgets (e.g., the floating chatbot) to the specific admin views the user names — do NOT expand them into layouts or public/guest pages. The user reverted a sitewide chatbot rollout (all 3 authenticated layouts + guest layout + 4 public views) back to reports-only: "the chatbot should only be in the report page on admin account". Keep such widgets as per-view includes (e.g., `<x-chatbot pageType="reports" />`) in the five `resources/views/admin/reports/*.blade.php` views — not in `layouts/admin`, `layouts/employee`, `layouts/app`, `layouts/guest`, or the standalone public views — and leave Alpine.js CDN / `[x-cloak]` / CSRF meta off public pages unless the user explicitly asks. Admin-only widgets stay admin-only (admin-only views plus admin middleware on the endpoint). Confidence: 0.85
- Prefers dead things deleted outright rather than archived: when reorganizing a project, wants unused, duplicate, obsolete files/folders/features removed so only what the system actually requires remains — and given the choice between "delete outright", "move to Archive/", and "delete code only, keep docs", picks delete outright. Expects anything genuinely essential (data files, uploads, fonts, images in use) to be verified as referenced before removal. Confidence: 0.7
- User is sensitive to subtle visual artifacts on images: a 1–2px Tailwind `ring-*` outline on the logo `<img>` tags reads as an unwanted "border" to them ("theres a border on the logo remove it"). Strip `ring`/`ring-*` classes from logo/image markup rather than leaving decorative outlines, and apply the fix to every logo instance project-wide (public views, layouts, sidebar partials). Confidence: 0.65
